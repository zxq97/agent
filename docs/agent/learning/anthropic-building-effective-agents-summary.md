# Anthropic《Building Effective Agents》深度摘要与业务 Agent 启发

原文：<https://www.anthropic.com/engineering/building-effective-agents>  
发布时间：2024-12-19  
整理日期：2026-07-01

## 1. 核心结论

这篇文章最重要的观点不是“如何搭一个更复杂的 Agent”，而是反过来提醒开发者：生产可用的 Agent 系统通常应该从简单、可组合、可评估的模式开始，只有在指标证明有必要时才增加复杂度。

它把 LLM 应用分成两类：

- **Workflow**：LLM 和工具沿着预定义代码路径运行。
- **Agent**：LLM 动态决定自己的流程和工具使用方式。

这个区分很关键。很多业务系统口头上叫 Agent，但真正适合生产的主链路往往更接近 workflow：业务流程、状态、权限、工具顺序、兜底策略由代码控制，LLM 只在局部做语义理解、决策或表达。

对应到业务 Agent，文章的底层建议可以概括为：

```text
先做简单 LLM 调用
再加检索 / 工具 / 记忆
再做固定 workflow
最后才考虑开放式 autonomous agent
```

## 2. 文章为什么强调“简单”

Anthropic 基于和多个行业团队一起构建 Agent 的经验，认为最成功的实现通常不是复杂框架，而是简单、可组合的模式。

原因有三个：

1. **复杂度会换来成本和延迟**
   Agentic system 往往要多次模型调用、多次工具调用、多轮状态传递。除非质量收益明显，否则不值得。

2. **复杂框架会遮住底层 prompt 和 response**
   框架能加速启动，但也容易让开发者看不清模型到底拿到了什么上下文、输出了什么、工具是怎么被调用的。生产排障时，这会变成大问题。

3. **很多任务并不需要 Agent**
   对大量业务功能来说，一个带检索和示例的单次 LLM 调用，或者一个固定 workflow，就已经足够。

这对业务 Agent 的启发是：不要一开始就问“要不要 ReAct / Plan & Execute / Multi-Agent”，而是先问：

- 单次 LLM 是否足够？
- 是否只需要 routing？
- 是否可以用固定 pipeline？
- 是否真的存在不可预测的多步任务？
- 增加自治能力后，是否有可量化收益？

## 3. Workflow 与 Agent 的边界

文章中 workflow 和 agent 的差异可以这样理解：

| 类型 | 控制权 | 适用任务 | 风险 |
| --- | --- | --- | --- |
| Workflow | 代码控制路径，LLM 执行局部任务 | 明确定义、可拆分、强业务约束 | 灵活性较低 |
| Agent | LLM 控制下一步和工具选择 | 开放式、多步、不易预定义 | 成本高、延迟高、错误会累积 |

业务系统大多天然偏 workflow，因为业务动作通常有确定边界：

- 查询库存。
- 查询订单。
- 发起退款。
- 修改地址。
- 查规则。
- 提交工单。
- 展示前端卡片。

这些动作不应该完全交给模型自由编排。模型可以决定“该不该查库存”“用户是否在问退款规则”，但真正执行时需要受代码、权限、状态机和白名单约束。

## 4. 基础构件：Augmented LLM

文章把增强 LLM 作为所有 agentic system 的基本构件。所谓增强 LLM，是给模型配上：

- retrieval：检索外部知识。
- tools：调用外部 API 或动作。
- memory：保留和读取历史信息。

它的关键不是“工具越多越好”，而是：

- 工具是否适合当前业务场景。
- 工具接口是否清楚。
- 模型是否知道什么时候用、怎么用、边界是什么。

对业务 Agent 来说，这一点非常实用。工具定义本身就是 prompt 的一部分，工具 schema、参数名、参数说明、错误返回、边界描述都会影响模型行为。

## 5. 常见 Workflow 模式

### 5.1 Prompt Chaining

Prompt chaining 是把任务拆成多个顺序步骤，一个模型调用的输出作为下一个模型调用的输入，中间可以插入程序化检查。

适合：

- 任务能被清楚拆成固定步骤。
- 每一步都比整体任务简单。
- 愿意用更高延迟换更高准确率。

业务例子：

- 先抽取订单问题类型，再生成回复。
- 先提取用户需求，再校验槽位，再生成导购话术。
- 先生成摘要，再检查摘要是否覆盖关键字段。

踩坑：

- 链路越长，延迟越高。
- 上游错误会传给下游。
- 如果中间没有 gate，就只是把一个大错误拆成多个小错误。

### 5.2 Routing

Routing 是先分类输入，再进入不同的专用流程。

适合：

- 用户请求天然分成多个类别。
- 不同类别需要不同 prompt、工具或模型。
- 一个大 prompt 处理所有情况会互相干扰。

业务例子：

- 客服：退款、售后、规则咨询、投诉、闲聊分别走不同链路。
- 导购：搜车、改取还车、规则解读、贵必赔、历史追问分别走不同 Stage。
- 成本优化：简单问题用小模型，复杂问题用强模型。

踩坑：

- 路由错了，后续全错。
- 分类边界要非常清楚，尤其是相近意图。
- 需要有“无法判断”的兜底，而不是强行归类。

### 5.3 Parallelization

Parallelization 是并行运行多个模型调用，再聚合结果。文章分成两类：

- Sectioning：不同子任务并行。
- Voting：同一任务多次尝试或多视角判断。

适合：

- 子任务彼此独立，可以并行提速。
- 需要多个视角提高置信度。
- 安全、合规、质量检查可以和主链路分开跑。

业务例子：

- 主回答生成和安全审核并行。
- 一个模型做用户意图，另一个模型做风险判断。
- 多个评估器分别检查事实、口径、格式。

踩坑：

- 聚合逻辑必须确定。
- 多模型结论冲突时，需要明确优先级。
- 并行会增加成本。

### 5.4 Orchestrator-Workers

Orchestrator-workers 是中央 LLM 动态拆任务，再分派给 worker LLM 或工具，最后汇总。

适合：

- 子任务数量和类型不可预知。
- 每次请求都可能涉及不同工作面。
- 任务足够复杂，值得让模型动态拆解。

文章举的例子包括代码修改和多源搜索。

业务例子：

- 复杂投研报告：行业、公司、财务、新闻、风险分开做。
- 复杂售前方案：需求、方案、竞品、报价、风险分开做。
- 研发 Agent：根据任务动态决定要读哪些文件、改哪些模块、跑哪些测试。

踩坑：

- 成本和延迟明显上升。
- 子任务状态同步复杂。
- Orchestrator 如果拆错，worker 做得再好也没用。
- 不适合高频、低延迟、动作边界明确的业务主链路。

### 5.5 Evaluator-Optimizer

Evaluator-optimizer 是一个模型生成结果，另一个模型评估并反馈，形成改进循环。

适合：

- 有明确评价标准。
- 输出可以通过反馈持续变好。
- 质量收益能抵消额外成本。

业务例子：

- 合同审查报告润色。
- 复杂搜索报告反复补证据。
- 营销文案多轮优化。
- RAG 答案生成后检查是否引用充分。

踩坑：

- 没有明确标准时，评估器容易变成“另一个主观模型”。
- 循环必须有停止条件。
- 不能把 evaluator 的意见当真理，也要被测试。

## 6. Autonomous Agent 适合什么

文章对 autonomous agent 的定位比较克制：它适合开放式问题，尤其是你无法预测步骤数量、也无法硬编码固定路径时。

典型条件：

- 任务目标明确，但路径不确定。
- 模型需要多轮使用工具。
- 每一步都能从环境获得 ground truth。
- 可以设置停止条件。
- 可以在关键点请求人类反馈。
- 对成本和延迟有容忍度。

文章提到的代表场景是 coding agent 和 computer use。

这对业务 Agent 的启发是：不要把 autonomous agent 当默认架构。它更像一种高复杂度方案，适合：

- 研发排障。
- 多文件代码修改。
- 多源调研。
- 长任务自动化。
- 操作型助手。

而不适合直接作为强交易链路主控，比如支付、退款、库存承诺、订单状态变更。

## 7. 工具接口比想象中更重要

文章最后专门讲了工具设计，也就是 Agent-Computer Interface（ACI）。

核心观点是：要像设计人机交互一样认真设计模型和工具之间的接口。

工具设计需要关注：

- 参数名是否直观。
- 参数描述是否明确。
- 是否包含边界和反例。
- 输出格式是否容易被模型生成。
- 是否避免让模型填写难以计算的格式。
- 是否通过 schema 让错误更难发生。
- 是否用大量样例测试模型怎么用工具。

文中有一个很实用的经验：某些工具格式对人类程序员是等价的，但对模型难度完全不同。比如让模型生成 diff，可能比让它输出普通文本更难，因为 diff 需要准确计算行号和上下文。

映射到业务 Agent：

- 不要只优化总 prompt。
- 工具 schema 本身要反复迭代。
- 对相似工具要写清边界。
- 尽量让参数贴近业务自然语言。
- 用白名单、枚举、结构化输出减少模型犯错空间。

## 8. 文章的生产实践原则

文章总结了三个原则：

1. **保持简单**
   能用单次调用就不用多步，能用 workflow 就不要直接上 autonomous agent。

2. **保持透明**
   要能看到系统怎么计划、怎么调用工具、每一步为什么发生。

3. **认真设计 ACI**
   工具接口、工具文档、工具测试是 Agent 可靠性的核心部分。

可以把这三个原则翻译成业务研发语言：

```text
少一点魔法，多一点工程可控性。
少一点框架黑盒，多一点 trace 和 replay。
少一点自由工具调用，多一点 schema、白名单和状态机。
```

## 9. 对业务 Agent 的落地启发

### 9.1 优先选择 Workflow，而不是裸 Agent Loop

大多数业务 Agent 的主链路应该是：

```text
Intent / Decision
-> Workflow / State Machine
-> Tool Call
-> Validation / Guardrail
-> Render
-> Memory
```

LLM 的角色是局部增强，而不是完全接管业务流程。

### 9.2 Complexity 必须由指标驱动

是否引入多步、并行、多 Agent、反思循环，应该看：

- 准确率是否提升。
- 成本是否可接受。
- 延迟是否可接受。
- badcase 是否减少。
- 可观测性是否仍然足够。

不能因为“Agent 架构更先进”就引入。

### 9.3 Framework 可以用，但不能被框架吃掉控制权

框架的价值是：

- 快速集成模型和工具。
- 提供 tracing、session、guardrail 等通用能力。
- 降低样板代码。

风险是：

- prompt 不透明。
- context 不透明。
- 工具调用细节不透明。
- 出问题后只能绕框架。

生产业务最好能做到：即使用框架，也知道底层每一步实际发生了什么。

### 9.4 Eval 和 Trace 是迭代核心

文章强调要测量性能并迭代实现。对业务 Agent 来说，这意味着：

- 每轮保存输入、上下文、模型输出、工具调用、工具结果、最终渲染。
- badcase 能一键回放。
- Prompt、context、tool schema 变更后能跑回归集。
- 不靠“感觉变好了”上线。

## 10. 和当前 AI 导购设计的映射

当前 AI 导购 V4 的设计和这篇文章的建议高度一致。

| Anthropic 模式 | AI 导购中的体现 |
| --- | --- |
| Routing | `DecideStage` 在搜车、反问、改取还车、规则、贵必赔之间分流 |
| Prompt chaining | `Decide -> FilterCode -> Search -> Guide -> Finalize` |
| Parallelization | 异步安全审核与主链路并行 |
| Augmented LLM | LLM + 实时菜单 + 库存搜索 + 会话记忆 |
| Workflow 优先 | V4 Pipeline 由代码固定控制，模型只做局部决策 |
| ACI 设计 | `v4_tools.go` 中严格定义工具参数和边界 |
| Guardrail | 安全审核、库存事实铁律、筛选码白名单、Finalizer 收口 |
| 测量和迭代 | Stage 日志、trace 信息、测试用例支撑 badcase 定位 |

这说明 AI 导购不是“少用了 ReAct”，而是在业务约束下选择了更合适的 agentic workflow。

## 11. 可以进一步借鉴的点

结合文章建议，当前业务 Agent 后续可以重点补强这些方向：

1. **更体系化的 eval**
   按意图分类、工具选择、筛选码、反问质量、库存事实、SSE 顺序分别建回归集。

2. **工具 ACI 测试**
   不只测最终结果，也测模型是否正确使用工具参数，尤其是相近工具边界。

3. **复杂度准入标准**
   每引入一次额外 LLM 调用、并行模型、反思循环，都要求有指标收益。

4. **Prompt / Context 版本化**
   每次 prompt、context prefix、tool schema 变更都能追踪版本，并支持回放对比。

5. **人类介入点**
   对高风险动作，如订单变更、退款、支付、客服工单，可以显式设计确认点，而不是让模型直接推进。

## 12. 最适合内部分享的一页总结

Anthropic 这篇文章的核心不是教大家搭一个很炫的 Agent，而是教大家少搭不必要的 Agent。

它建议从简单 LLM 调用开始，逐步引入检索、工具、记忆、routing、prompt chaining、并行、评估循环，只有当任务路径不可预测且确实需要模型动态决策时，才使用 autonomous agent。

对业务系统来说，最稳的形态通常是：

```text
LLM 做语义理解和局部决策
代码控制业务流程和状态
工具提供真实数据和动作
校验与 guardrail 兜住风险
trace / eval 支撑持续迭代
```

这也是当前 AI 导购 V4 的方向：不是让模型自由循环，而是把模型放进可控 Pipeline，让它在明确边界内发挥自然语言理解和导购表达能力。
