# AI 导购设计亮点总结

本文总结租车 C 端 AI 导购在当前项目中的核心设计亮点，以及这些设计分别解决的问题、有效规避的风险。相关主链路主要位于 `logic/agent` 与 `common/dto/agent`。

## 一句话总结

AI 导购的核心设计是：模型负责自然语言理解与表达，系统负责状态、约束、库存、筛选码、审核和收尾。

这样既保留了 AI 导购的自然对话体验，又用确定性工程逻辑兜住租车业务里最容易出事故的地方：搜错城市、编库存、筛选码幻觉、反复追问、空结果、历史状态污染和流式卡死。

## 1. V4 流水线拆分，职责边界清晰

V4 主链路通过责任链组织：

```text
PreRoute -> Decide -> Rules -> PriceProtect -> ModifyLocation -> FilterCode -> Search -> Guide -> Clarify -> Finalize
```

对应入口在 `logic/agent/v4_orchestrator.go`。

设计亮点：

- 每个 Stage 只做一件事：前置分流、决策、规则解读、贵必赔入口、改取还车、筛选码生成、搜车、导购解释、反问、收尾。
- 每个 Stage 都能独立打日志、独立兜底、独立定位问题。
- 复杂导购链路不再压在一个大函数或一次大模型调用里。

解决的问题：

- 大模型同时做意图判断、选码、搜车、出话术时，错误很难定位。
- 某一步失败容易拖垮整轮对话。
- 新能力接入时容易破坏老链路。

有效避免：

- 选错工具、搜错城市、前端卡死、done 帧漏发。
- 一次模型调用包办所有业务导致的不可控和难回放。

## 2. DecideStage 只做需求理解和工具决策

`DecideStage` 位于 `logic/agent/v4_stage_decide.go`，Prompt 位于 `logic/agent/v4_decide_prompt.go`。

它的职责是：

- 先流式输出一段用户可见的话术。
- 再通过 function calling 选择工具：`search_vehicles`、`ask`、`modify_location`、`interpret_rules`、`price_protection_entry`。
- 搜车时只产出 `need_delta`，不直接产出 `filter_codes`。

设计亮点：

- 把“理解用户想要什么”和“从菜单里选哪个筛选码”拆开。
- 决策模型不接触复杂实时菜单，降低 prompt 负担。
- 支持纯文本回复：闲聊、越界、历史追问可以不调用工具。

解决的问题：

- 模型直接从菜单里选码，容易漏维度、选错码、编不存在的码。
- 同一轮同时理解意图和选码，prompt 复杂度高，稳定性差。

有效避免：

- “豪华电车”只抓到“电车”漏掉“豪华型”。
- “低一点”被模型误选到最低价档导致搜空。
- 模型生成不存在的筛选项。

## 3. FilterCodeStage 单独生成筛选码，兼顾确定性和模型能力

`FilterCodeStage` 位于 `logic/agent/v4_stage_filtercode.go`。

它把 `need_delta + 会话 needs + 实时菜单` 转成最终 `filter_codes`。

设计亮点：

- 静态规则能确定命中时，直接走静态快路，跳过 lite LLM。
- 有模糊需求时，再交给 FilterSelector 做语义选码。
- 无 selector、无菜单或 LLM 失败时，不阻断主流程，交给后续静态召回兜底。
- 相对预算如“低一点/贵一点”用上一轮真实价格做锚定。

解决的问题：

- 筛选码是导购搜索中最容易出错的环节，需要比纯模型更强的确定性约束。
- 实时菜单变化时，模型不能随意编码。
- 相对预算必须基于上一轮真实结果，而不是模型凭感觉选档。

有效避免：

- 菜单码幻觉。
- 价格档漂移。
- LLM 失败导致整轮失败。
- 搜索条件过窄或过宽。

## 4. 多轮需求状态用 need_delta 和置信度衰减维护

需求状态定义在 `common/dto/agent/internal.go`，更新逻辑在 `logic/agent/search/need_state.go`。

用户需求不是简单覆盖，而是通过以下操作维护：

```text
ADD / UPDATE / DECAY / NEGATE / DELETE / REINFORCE
```

设计亮点：

- 每条需求带 `type`、`value`、`hardness`、`confidence`、`negative`、轮次信息。
- 每轮自然衰减，长期未强化的需求会逐渐退出活跃状态。
- 新旧需求冲突时，旧需求会被衰减或删除。

解决的问题：

- 多轮对话中用户会改口，历史条件不能永久生效。
- 旧条件若继续参与搜索，会把结果钉死。

有效避免：

- 用户先说“丰田 7 座”，后面说“看小米”，系统仍搜“小米 + 7 座”。
- 用户从具体车型改成“经济型/SUV/更便宜的”后，旧车型仍然锁死搜索。
- 越聊越偏、越筛越空。

## 5. 反问结构化，不做裸问

反问渲染在 `logic/agent/v4_stage_clarify.go`。

设计亮点：

- 模型想问用户时，必须调用 `ask` 工具。
- `ask` 会转成标准 `Clarification`，带问题、选项、可跳过、可自由输入。
- 用户回答后由 `PreRouteStage` 解挂，转成下一轮可推进的输入。

解决的问题：

- 纯文本里问“你几个人坐？”时，前端没有选项，后端也不知道用户在回答哪个槽位。
- 反问如果不进入状态机，下一轮承接会很差。

有效避免：

- 裸问导致体验割裂。
- 同一个问题连续追问。
- 用户点击“暂不指定”后仍被逼填。
- 用户回答无法映射到具体需求槽位。

## 6. 库存事实必须真搜，避免模型空口承诺

V4 Prompt 中强调“库存事实铁律”：

- 某品牌、车型、能源、价位有没有车，只能由本轮 `search_vehicles` 的真实返回决定。
- 用户问 “A 和 B 哪个好”“有没有 Model Y”“要奥迪还是宝马” 时，必须先搜库存，再回答。

设计亮点：

- 把大模型的常识回答限制在真实库存之后。
- 历史空结果不能直接代表本轮事实，因为历史搜索可能带着不同约束。

解决的问题：

- 租车业务的可售库存强依赖城市、时间、门店和实时供给。
- 不能因为常识上某车型热门，就暗示平台当前有车。

有效避免：

- 虚假承诺“有这款车”。
- 没查就说“没有车”。
- 脱离库存做品牌对比。
- 用旧搜索结果误判新问题。

## 7. 空结果有放宽策略，不直接走死路

空结果放宽逻辑位于 `logic/agent/v4_search_relax.go`。

设计亮点：

- 搜空后按优先级放宽软条件，价格优先。
- 硬需求不随意放宽。
- 放宽后会明确告知用户，比如“帮你放宽了下价格”。

解决的问题：

- 租车搜索很容易被预算、车型、能源、服务等条件卡空。
- 直接告诉用户“没车”会降低转化，也没有给出替代方案。

有效避免：

- 空结果直接失败。
- 静默修改用户条件。
- 硬条件被错误放宽。
- 用户不知道系统为什么给了这些车。

## 8. GuideStage 基于真实搜索结果做个性化导购解释

`GuideStage` 位于 `logic/agent/v4_stage_guide.go`。

搜车成功后，它会再做一层导购解释：

- 结合真实搜到的车。
- 结合用户画像。
- 输出“为什么这些车适合你”的短话术。
- 再输出可点击的筛选胶囊和车型对比入口。

设计亮点：

- 文案先流式输出，再下发卡片和快捷操作。
- 胶囊 JSON 会经过白名单和菜单校验。
- 车型对比只从真实结果里选。

解决的问题：

- 搜车卡片只是列表，用户还需要导购解释。
- 单纯堆参数不能回答“为什么适合我”。

有效避免：

- 推荐理由空泛。
- 快捷胶囊编造不存在的筛选项。
- 先出卡片再补解释造成体验割裂。

## 9. 用户画像单独沉淀，不污染硬筛选

用户画像定义在 `common/dto/agent/internal.go`，合并逻辑在 `logic/agent/memory_manager.go`。

画像字段包括：

- `trip_scene`：出行场景。
- `companions`：同行人。
- `price_sensitivity`：价格敏感度。
- `style_preference`：调性偏好。
- `confidence`：画像置信度。

设计亮点：

- 画像用于话术和推荐解释，不直接变成硬筛选条件。
- 每轮通过 `profile_patch` 增量更新。
- 和 slot 级搜索约束分层存储。

解决的问题：

- “带爸妈孩子”“商务接待”“接送机”这类高层语义需要被记住。
- 但这些语义不能都变成强筛选，否则容易搜空。

有效避免：

- 把软画像误当硬条件。
- 每轮从零理解用户。
- 话术无法体现个性化。

## 10. SSE、审核和收尾做成统一管道

审核逻辑在 `logic/agent/guardrail/audit_async.go`，最终收尾在 `logic/agent/v4_stage_finalize.go`。

设计亮点：

- 用户输入和模型输出都进入异步审核。
- 输出按片段送审，不阻塞主流程。
- 命中安全拦截后，通过 `done.reason = ism_guardrail` 统一通知前端。
- `FinalizeStage` 统一负责 done 帧、思考态关闭、memory apply 和落库。

解决的问题：

- 流式输出场景下，安全审核、SSE 关闭、done 帧和前端 loading 很容易互相打架。

有效避免：

- `send-on-closed-channel`。
- 审核命中后残留流式内容继续覆盖兜底文案。
- 思考态 start 没有对应 done。
- 前端一直 loading。

## 设计收益汇总

| 设计 | 解决的问题 | 避免的风险 |
| --- | --- | --- |
| V4 Stage 流水线 | 链路复杂、耦合高、难排查 | 一个点失败拖垮整轮 |
| Decide 只产 need_delta | 模型负担过重、选码不稳 | 筛选码幻觉、漏维度 |
| FilterCode 独立选码 | 菜单实时变化、预算相对表达难处理 | 价格漂移、选错码 |
| Need 状态衰减 | 多轮改口、旧条件残留 | 历史条件钉死搜索 |
| 结构化反问 | 裸问无法承接 | 反复追问、槽位丢失 |
| 库存事实铁律 | 模型凭常识答库存 | 虚假承诺、假装查过 |
| 空结果放宽 | 条件过严搜空 | 直接失败、静默改条件 |
| Guide 个性化解释 | 搜索列表缺少导购感 | 推荐理由空泛 |
| 用户画像分层 | 高层偏好难沉淀 | 软偏好误变硬筛选 |
| 异步审核 + Finalize | 流式收尾复杂 | 前端卡死、安全残帧 |

## 适合对外表达的版本

这个 AI 导购不是简单把用户问题丢给大模型回答，而是做了“模型理解 + 工程决策 + 真实库存 + 状态管理”的混合架构。

模型主要负责理解用户自然语言、判断下一步动作、生成自然导购话术；工程链路负责把需求转成可控筛选条件，基于真实库存搜索，并对多轮状态、反问、空结果、安全审核和前端流式体验做确定性保障。

因此它既能像真人导购一样自然交流，又能避免租车业务中最常见的 AI 风险：编库存、乱选筛选项、反复问用户、历史条件污染、搜空后无解，以及流式响应收尾不稳定。
